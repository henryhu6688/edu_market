# 6月13日开发教训

## SSE 流式输出

### 问题 1：前端截断只显示前几十字

**现象**：后端日志显示完整回复已生成，DB 中也是完整的，但前端只显示前 30-60 字。

**根因**：`reader.cancel()` 在收到 `done` 事件后立即销毁 ReadableStream，TCP 缓冲区中尚未读取的 delta 数据全部丢失。

**修复**：`reader.cancel()` → `break`，让 while 循环自然退出，不丢缓冲数据。

### 问题 2：模拟流式 vs 原生流式

**旧实现**：
```
callLLM(stream: false) → 等 3-10 秒拿完整回复（首字延迟 3-10s）
  → streamAnswer() 逐字发 delta（200 字 × 20ms = 4 秒，客户端感受到的全是空等）
  → 发 done → 前端渲染
```

**问题**：
- 假流式——不是 LLM 实时出字，是后端拿到全文后自己拆开，用户感受不到"即时响应"
- 逐字拆发慢（4 秒 200 字），done 和最后几个 delta 可能同时到达，前端解析时序错乱

**新实现**：
```
有 tool_calls 的轮次：
  callLLM(stream: false) → 解析 tool_calls → 执行 → 继续循环

无 tool_calls 的最终轮次：
  callLLMStream(stream: true) → DeepSeek 返回 SSE 流
    → 引擎逐条转发 delta 到前端（首字延迟 ~200ms）
    → 前端实时逐字渲染（打字机效果）
```

**关键约束**：LLM API 的 `stream: true` 和 `tools` 参数不能同时用。所以 tool call 轮次保持非流式，只有最终文本回复才用流式。

## DeepSeek 模型兼容性

### 模型选择踩坑

| 模型名 | 问题 |
|--------|------|
| `deepseek-chat` | 解析到 `deepseek-v4-flash`，生成中随机截断（finish_reason=stop 但内容只有 40 字） |
| `deepseek-v3` | 错误："supported model names are deepseek-v4-pro or deepseek-v4-flash" |
| `deepseek-v4-pro` | 要求 `reasoning_content` 字段必须保存并回传，否则报 400 |
| `deepseek-v4-flash` | 同 pro，也要求 reasoning_content |

最终用 `deepseek-chat`（flash 的别名），prompt 加"每次回复必须完整，不要中途停止"缓解截断。

### reasoning_content 处理

**现象**：deepseek-v4-pro 报 400 "The `reasoning_content` in the thinking mode must be passed back to the API"

**根因**：
1. LLM 返回的 assistant 消息 JSON 中有 `reasoning_content` 字段（思考过程）
2. 存 DB 时只存了 `content`，没存 `reasoning_content`
3. 下次 loadContext 加载历史拼回上下文，API 发现之前的 assistant 消息缺少 `reasoning_content`
4. 报 400

**修复三处**：
1. `model/message.go`：Message 模型新增 `ReasoningContent string \`gorm:"type:text"\``
2. 引擎 Run() 存 assistant 消息时：`ReasoningContent: choice.Message.ReasoningContent`
3. 引擎 loadContext() 加载时：
   - 旧消息（ReasoningContent 为空）跳过，不拼回上下文
   - 新消息恢复 `msg.ReasoningContent = m.ReasoningContent`
4. **重要**：tool_calls 轮次的 assistant 消息也必须在内存中带上 `ReasoningContent` 和 `Content`，不然 LLM 下一轮请求同样报 400

## Tool 调用死循环

**现象**：平台没资料时，`query_materials` 被连续调用 9 轮，10 轮上限用完才停。

**根因**：
- tool 空结果返回"未找到匹配的课程"，LLM 理解为"可能关键词没对，换一个试试"
- 没有防重复机制

**修复**：
1. 空结果文案改为"平台暂无相关资料，建议换个方向"，明确告知
2. System Prompt 新增："同一 tool 连续 2 次无结果就不要再调了，直接告知用户实际情况"
3. System Prompt 新增："平台没有的资料不要编造"

## 前端消息显示问题

### tool 结果不应出现在聊天中

**现象**：刷新页面后聊天区出现 `[{"id":1,"name":"编程开发"},...]` 和 `未知工具: query_courses` 这样的 raw JSON。

**根因**：`loadMessages` 加载全部消息（含 role=tool），未过滤。

**修复**：加载时 `.filter(m => m.role !== 'tool')`

### thinking 提示 vs loading 动画

- thinking 文字弹出（"正在查询: xxx"）太吵，去掉
- loading 三点动画保留，用户需要感知系统在工作

## Tool 名称不一致

**现象**：LLM 报"未知工具: query_courses"

**根因**：tool map key 是 `query_materials`，但 tool Definition().Name 返回的是 `query_courses`。LLM 看定义调 `query_courses`，map 里没有。

**修复**：常量改为 `ToolQueryMaterials = "query_materials"`，System Prompt 也同步改为 `query_materials`

## 日志系统

### slog 不带行号

slog handler 默认不输出源码位置。需要 `&slog.HandlerOptions{AddSource: true}`。

### Tool 日志要显示内容

日志记 `result_len` 没用——出问题时需要看具体返回了什么。改为截取前 200 字显示。

### Tool 日志要在执行后打

`slog.Info` 写在 `tool.Execute` 之前，拿不到结果。日志顺序 = 执行顺序。

### request_id 全链路

1. middleware 生成 UUID → `c.Set("request_id")`
2. controller 读取 → 传给 AgentService.Chat()
3. AgentService 传给 AgentEngine.Run()
4. 所有 slog 调用带 `request_id`

grep 一个 ID 就能追全链路。

## 配置与安全

### 敏感数据不能硬编码

测试 setup_test.go 中的 `jwt.secret`、`database.password`、`ai.api_key` 必须从 `config/app.yml` 读取：
```go
func readConfigYAML(key string) string {
    v := viper.New()  // 独立实例，不和全局 viper 冲突
    // ...
}
```

### 配置文件同步

`app.example.yml` 和 `app.yml` 结构必须完全一致，只差敏感字段值。改结构时两个文件同时更新。

### pre-commit hook

`.githooks/pre-commit` 在 master 分支上拦截非 merge 的 commit。
